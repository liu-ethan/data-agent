# 基于 Spec 的开发流程

> 目标：把开发计划从“阶段任务列表”拆成可实现、可测试、可评审的规格。任何核心能力在开工前都必须能回答：输入是什么、输出是什么、谁可以调用、什么情况下拒绝、如何证明完成。

## 1. Spec 状态

| 状态 | 含义 | 能否开发 |
| --- | --- | --- |
| `Draft` | 方向明确，但字段、边界或验收仍可能变化 | 只能做探索或 PoC |
| `Ready` | 输入输出、不变量、错误语义和测试证据清楚 | 可以进入实现 |
| `Implemented` | 已按 spec 完成代码和测试 | 可以接入上游链路 |
| `Verified` | 通过固定评测、Trace 和人工抽查 | 可以写入 README 或简历事实 |
| `Deferred` | 本轮不做，仅保留边界说明 | 不能作为已实现能力宣传 |

## 2. 开工前检查

每个 spec 进入 `Ready` 前必须具备：

- 清晰的 `In Scope` 和 `Out of Scope`；
- 至少一个正常路径和一个拒绝/异常路径；
- Pydantic 或等价结构的数据契约；
- 上游调用方和下游依赖；
- 权限、安全、预算和持久化边界；
- Trace 字段；
- 单元测试、集成测试或评测用例；
- 明确的降级策略。

新增 spec 优先复制 [specs/SPEC_TEMPLATE.md](./specs/SPEC_TEMPLATE.md)，再按能力域删改。

## 3. 实现规则

- 先实现确定性边界，再接入 LLM。
- 所有数据库访问必须经过 Gateway 或 Repository，不能在 Node 里临时直连。
- 大对象通过 `result_id`、`artifact_id`、`context_id` 引用，不无界塞进 State 或 Prompt。
- Prompt 只接收 `PromptContextBuilder` 投影后的最小上下文。
- 权限、Schema、指标口径和长期记忆必须有版本或来源，不从模型输出反推成事实。
- 未通过固定测试的指标只能写成“目标”或“待验证”，不能写成“已达到”。

## 4. Spec 变更规则

当实现中发现原 spec 边界不够清楚时，先改 spec，再改代码。常见需要回写 spec 的情况：

- 新增或删除字段；
- 新增允许 SQL 形态、图表类型或写入表；
- 改变错误码、状态机或重试预算；
- 调整权限判断位置；
- 改变 Artifact、Checkpoint 或长期记忆的保存内容；
- 评测发现原验收标准不可复现。

## 5. 全局完成定义

一个开发项只有同时满足以下条件才算完成：

- 代码行为和对应 spec 一致；
- 正常、异常、越权和边界路径都有测试；
- Trace 能解释关键决策和拒绝原因；
- 没有新增绕过权限、Gateway 或 Checkpoint 的旁路；
- 文档中“已实现”和“设计目标”没有混写；
- 评测数字能定位到数据集版本、代码版本和计算方式。
