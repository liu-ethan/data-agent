# 需求总览

> 返回 [需求文档索引](./需求文档.md)

## 1. 项目目标

开发一个面向电商经营分析场景的 DataInsight Agent。

用户输入自然语言业务问题，系统自动完成：

```text
自然语言问题 -> 意图识别 -> Schema Linking -> SQL 生成 -> 权限校验 -> 沙箱执行 -> 错误修复 -> 图表规划 -> 分析结论
```

本项目目标不是做普通 Text-to-SQL Demo，而是体现 AI 应用开发中更贴近企业场景的能力：

- LangGraph 状态图编排（简单 ReAct / 复杂 Coordinator）
- Tool Calling
- Schema Linking
- 注册登录（JWT）与角色权限
- 权限校验（analyst 只读 / admin 受控可写）
- SQL 沙箱执行
- SSE 流式输出与结构化 Trace / AuditLog
- Session + 跨 Session 结构化长期记忆
- 执行反馈修复
- Agent 评测

项目需要适合校招简历和面试深挖，但避免为了堆概念而过度设计。

## 3. 设计原则

1. 简单问题走单 Agent ReAct，复杂问题走 Coordinator 多 Agent；主编排采用 LangGraph，工具与记忆抽象采用 LangChain。
2. 能用确定性代码解决的问题，不交给模型判断。
3. 所有 SQL 执行必须经过权限校验和沙箱执行；角色来自服务端鉴权，不信任客户端自报。
4. 项目第一目标是主链路可跑通、可展示、可解释。
5. Tool 调用统一经 Tool Registry 治理；可扩展 MCP / 用户 Tool Manifest，但仍须经过权限与审计。
6. 后端提供结构化 Trace / AuditLog（与 Prompt 分离）；写操作必须可追溯。

## 4. 技术栈

前端：

- React
- Vite
- TypeScript
- TailwindCSS
- Recharts

后端：

- Python
- FastAPI
- SQLite
- Pydantic
- JWT 鉴权
- SSE（`text/event-stream`）

Agent 编排：

- **选型：LangGraph（编排）+ LangChain（LLM / Tools / Memory 抽象）**
- 理由：
  - 条件路由天然支持「简单 ReAct / 复杂 Coordinator」分流
  - 状态图、checkpoint、trace 便于可观测与评测
  - SQL Guardrail、权限、沙箱仍作为确定性独立模块，不交给黑盒 SQL Agent
  - 结构化长期记忆可直接落在现有 SQLite 栈上
- 不采用：以纯自研 AgentLoop 为主、以 CodeBuddy SDK 为主（README 可写后续可适配）
- 禁止：直接使用黑盒 SQL Agent 绕过权限校验与沙箱执行

模型接口：

- 兼容 OpenAI API 格式
- 通过 `.env` 配置：

```env
OPENAI_API_KEY=
OPENAI_BASE_URL=
OPENAI_MODEL=
JWT_SECRET=
ADMIN_INVITE_CODE=
```

评测：

- Python 脚本
- JSON 评测集
- 输出 `eval_result.json`

可观测：

- 结构化 JSON 日志 + `logs/audit.jsonl`
- `request_id` / `trace_id` 串联节点、Tool、SSE

## 8. 面试讲法

一句话介绍：

> 这是一个面向电商经营分析的企业数据 Agent。用户先通过营销感登录页进入工作台；系统用 LangGraph 编排：简单问题走 ReAct，复杂问题走 Coordinator；SSE 流式展示节点与工具轨迹；SQL 执行前做 Schema Linking、按角色权限校验和沙箱执行，失败后基于错误反馈修复，最后输出图表和业务结论。

为什么简单用 ReAct、复杂用 Coordinator：

> 单指标、单时间窗、路径清晰的问题用 ReAct 足够，延迟低、轨迹也好读。多指标对比、多步归因、跨域 JOIN 或需要多工具协作时，再用 Coordinator 把 Schema、SQL、图表/洞察等子 Agent 拆开，避免一个巨型 prompt 既慢又难控。路由用规则优先的 ComplexityRouter，能确定的不交给模型猜。

为什么选 LangGraph 而不是自研 Loop 或 CodeBuddy SDK：

> LangGraph 的状态图和条件边直接对应分流与修复环；LangChain 覆盖 Tool / Memory 抽象。SQL 安全仍是自研确定性模块。自研 Loop 在 Coordinator + 长期记忆下成本过高；CodeBuddy 偏厂商锁定，更适合后续适配而不是主栈。

为什么要做 Tool Registry：

> Agent 调用工具时需要可治理：每个 Tool 有名称、描述、参数 Schema、风险等级和权限策略。无论内置 Tool、MCP 还是用户上传 OpenAPI Tool Manifest，都复用同一套权限和审计机制。

为什么要做 SQL 沙箱与角色差异：

> LLM 不能直连业务库。生成 SQL 后必须经 Guardrail：analyst 只读并拦截敏感字段；admin 可受控执行 INSERT/UPDATE/DELETE，但仍禁 DDL、多语句和系统表。执行走沙箱连接，写操作进入 AuditLog，保证可用性与可追溯。

为什么 Trace / AuditLog 要和 Prompt 分开：

> 前端 `agent_trace` 和 SSE 负责可解释展示；后端 AuditLog 负责排查与写操作审计。完整工具日志默认不进 Prompt，避免噪声和泄密，这和常见 AI 应用里「审计日志 ≠ 会话记忆」的做法一致。
