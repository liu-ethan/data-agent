## 1. README 要求

README 必须包含：

1. 项目简介
2. 为什么不是普通 Text-to-SQL
3. 架构图
4. 本地启动方式（含注册登录、邀请码说明）
5. 营销登录页与工作台截图
6. Agent Trace / SSE 截图
7. SQL Guardrail 与角色差异说明（analyst 只读 / admin 受控可写；禁全部应用表）
8. 权限校验说明（含敏感字段 `users.name/phone/email/id_card`）
9. SQL 沙箱执行说明
10. Trace / AuditLog 说明（含 `route_decision`）
11. Session 槽位 / 偏好 JSON + 最近摘要说明（非笼统「结构化长期记忆」）
12. 评测结果
13. 失败案例分析
14. 后续扩展方向
15. 开篇标明：规格以 docs 为准；未实现模块时启动命令为「目标形态」

后续扩展方向可以写：

- 接入 MCPToolProvider
- 支持用户上传 OpenAPI Tool Manifest
- 适配 CodeBuddy SDK
- 接入真实企业数仓
- 增加更严格的语义评测

主编排已选型 LangGraph + LangChain；上述扩展不替代主链路，也不包含真实支付 / 订单 / CRM 外部系统接入。

## 2. 开发阶段

### Phase 1：项目初始化

目标：

- 创建前后端项目
- 配置环境变量（含 `JWT_SECRET`、`ADMIN_INVITE_CODE`）
- 初始化 SQLite：8 张业务表 + 应用表（`app_users`、`chat_sessions`、`session_turns`、`user_preferences`、`user_analysis_summaries`）
- 生成业务模拟数据（含 users 敏感字段列）
- 实现结构化日志骨架（`request_id` / JSON 日志）
- 实现 `/api/schema`（仅业务表）

验收：

- 后端能启动
- 前端能启动
- 数据库能生成
- `/api/schema` 能返回 8 张业务表结构（不含应用表）

### Phase 2：鉴权 + 基础查询闭环

目标：

- 实现注册 / 登录 / me（JWT）
- 实现营销感登录注册页 `/`，登录后进入 `/app`
- 实现 `POST /api/chat`（先可 sync，再切 SSE；或直接 SSE）
- 接入模型 API
- 实现基础 SQL 生成和执行（**开发期可先直连，但不得作为默认可演示路径**；Phase 4 前合入 Guardrail，或本阶段即挂最小只读校验）
- 角色从 JWT 注入 `AgentState`

验收：

- 可注册 analyst；带邀请码可注册 admin
- 未登录无法进入工作台
- 至少 5 个示例问题能成功返回结果
- 前端可以展示回答、SQL 和表格
- 明确：无 Guardrail 的临时执行路径不得进入 README Demo / 默认可运行分支

### Phase 3：LangGraph 节点拆分 + SSE

目标：

- 实现 AgentState（含 `user_id` / `request_id` / `trace_id` / `route_mode` / `slots`）
- 接入 LangGraph 状态图编排（Phase 5 前可先单路径执行，仍产出并记录 `route_mode`）
- 实现 IntentAnalyzer（轻量模型：封闭枚举 intent + 建议 route_mode + 薄词表 slots；prompt 不含全库 Schema）、ClarificationChecker、SchemaRetriever（metric key→SQL 口径）、SQLGenerator、AnswerComposer
- 代码维护 `METRIC_VOCAB` / `DIMENSION_VOCAB`（与口径表对齐；建议 `agent/vocab.py`）
- `POST /api/chat` 以 SSE 推送 `node_*` / `sql` / `answer` / `done`
- 返回并展示 agent_trace（含 `route_decision` 更佳）

验收：

- 每次请求都有 Agent Trace（前端随 SSE 更新）
- IntentAnalyzer 能产出 intent、slots、route_mode；分流看 route_mode 而非 intent
- Intent prompt / 输入不含全量业务表字段列表
- SchemaRetriever 只返回相关业务表字段，并能把 slots.metrics 映射到口径
- 模糊问题能返回澄清问题并结束（不跑 SQL）
- README 能解释 LangGraph 主图、双模式与节点职责

### Phase 4：Tool Registry、权限、沙箱与 AuditLog

目标：

- 实现轻量 Tool Registry + Pre/Post Tool 审计钩子
- 实现 5 个内置 Tool
- 实现 SQLGuardrail（按角色）
- 实现字段级权限校验
- 实现 SQLSandboxExecutor（analyst 只读 / admin 可写）
- 落盘 `logs/audit.jsonl`（脱敏）

验收：

- analyst：写操作与敏感字段被阻断；DDL 被阻断
- admin：允许 INSERT/UPDATE/DELETE；DDL / 多语句 / **全部应用表**（`app_users`、`chat_sessions`、`session_turns`、`user_preferences`、`user_analysis_summaries`）仍阻断
- SQL 必须通过 Guardrail 才能执行；无旁路直连
- Tool 调用有 trace + AuditLog 记录

### Phase 5：错误修复、分流与记忆

目标：

- 实现 SQLRepairer
- 实现 ComplexityRouter：采纳 IntentAnalyzer 的 route_mode，规则可硬覆盖；挂接 ReAct 子图与 Coordinator 子图（共用 Tool / Guardrail）
- 实现 Session 槽位（`session_turns`）+ 长期记忆轻量形态：`preferences_json` + 最近摘要列表（无向量）
- Memory 读/写挂在主图两端（两模式共用），不要做成 Coordinator 专属步骤
- 支持多轮追问与跨 Session 偏好/摘要复用

验收：

- 至少 3 类 SQL 错误能自动修复
- 简单问题走 ReAct，复杂问题可进入 Coordinator；`route_source` 可区分 model / rule_override
- 同 session 追问能继承槽位；跨 session 能读到偏好 JSON 或最近摘要
- “那按城市拆一下”这类追问能继承上下文
- 修复后的 SQL 会重新经过 Guardrail
- Memory 按 session_id / user_id 隔离；长期记忆仅为偏好 JSON + 摘要列表

### Phase 6：图表与前端完善

目标：

- 实现 ChartPlanner
- 前端展示折线图、柱状图、饼图
- 优化 SSE Agent Trace 展示
- 打磨营销登录页与工作台体验
- 侧栏展示当前用户角色（不可客户端切换）

验收：

- 趋势问题展示折线图
- TopN 问题展示柱状图
- 占比问题展示饼图
- 登录页具备营销视觉；工作台可作为 Demo 展示
- admin 写操作结果在 UI 有明确提示

### Phase 7：评测与文档

目标：

- 创建 30 条评测问题（含权限拒绝、admin 写操作安全边界）
- 实现评测脚本
- 输出 eval_result.json
- 完善 README
- 补充截图和架构说明

验收：

- 一条命令能运行评测
- README 包含完整项目介绍、架构图、启动方式和评测结果
- 项目可以用于简历展示

## 3. Cursor 开发要求

请严格按照 Phase 1 到 Phase 7 顺序开发。

每完成一个 Phase，必须：

1. 运行项目或相关测试
2. 检查验收标准
3. 修复明显问题
4. 再进入下一阶段

开发原则：

- 不要一次性生成全部代码
- 优先保证主链路可运行
- 再补充安全、记忆、评测和前端体验
- 不要为了展示概念而引入不必要复杂度
- 每个 Agent 节点保持独立文件
- 安全校验和沙箱执行必须独立实现
- AuditLog 与 Prompt / 长期记忆分离
- README 随功能同步更新；对外描述与 `docs/` 保持一致（主链路含 intent/slots/route_mode；记忆为偏好 JSON + 摘要列表）
- **跨 Phase 安全硬约束**：任意可演示 / 默认 chat 路径上的 SQL 必须经 SQLGuardrail 再进沙箱；禁止长期保留「节点直连 DB 执行」旁路；Phase 2 临时直连不得进入 Demo 默认分支
