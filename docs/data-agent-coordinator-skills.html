Q1

可信查询Skill

在权限范围内通过Schema Agentic RAG、SQL网关和受限结果筛选完成多轮问数。

Input · QueryTask

metric_id、维度、筛选、确定时间范围、权限

Output · SkillResult

result_id、result_summary、列/行数、指标与Schema版本、data_as_of、错误状态

RuleQ01

权限与口径

按metric_id加载指标公式、时间字段、固定筛选和版本，再过滤无权限对象。

out: metric_spec + allowed_catalog
LLMQ02

生成表级检索问题

把指标、维度和筛选改写为表级检索问题。

out: table_queries[]
ToolQ03

召回候选表

使用BM25与向量检索召回候选表。

out: candidate_tables[]
ToolQ04

表内字段与JOIN

在候选表内召回字段，关系图补全JOIN路径。

out: schema_candidates[]
RuleQ05

Schema覆盖检查

检查指标、维度、筛选、时间字段和JOIN路径是否完整。

complete / gap / ambiguous
LLMQ06

生成SchemaGap

把缺失概念、字段用途、约束和已排除候选整理为补检问题。

out: schema_gap
ToolQ07

全局字段补检

全局检索缺失字段，将字段所属表加入候选表。

回到Q04，最多2轮 / 无新增 → HITL
LLMQ08

生成查询骨架

只引用metric_id、最小Schema和审核JOIN关系，不展开指标公式。

out: query_skeleton
RuleQ09

确定性指标编译

MetricCompiler注入审核公式、固定筛选、时间字段和粒度，生成最终SELECT。

out: compiled_select
Shared RuleQ10

SQL网关·只读策略

检查权限、表关联和重复统计；结合EXPLAIN拒绝高成本查询。

unsafe / too broad → reject
Shared ToolQ11

只读执行并保存

先创建WRITING元数据，再流式写.part；完成后原子重命名并标记READY。

too large → 删除临时文件 / out: result_id
Schema Agentic RAG：Q02—Q07构成“表召回—表内字段召回—关系图补全—覆盖检查”闭环；覆盖不足时生成SchemaGap执行全局字段补检，将命中字段所属表加入候选表后回到Q04，最多2轮。
受限多轮：已有列的筛选、排序、选列和TopN经规则校验后由DuckDB读取Parquet，生成带parent_result_id的新结果；新增指标、维度或缺失字段时重新进入Q01。
大结果边界：前端只分页读取已落盘Parquet；不按页回查业务库，也不用分库分表绕过扫描和结果限制。

设计亮点

  • 先表、后字段、再JOIN；漏表时通过SchemaGap全局字段补检。
  • LLM只生成查询骨架，指标公式由MetricCompiler注入。

解决问题

  • 几千张表无法全部塞进上下文。
  • LLM猜指标公式、猜JOIN或绕过权限。
W1

受控写入Skill

MVP只开放1～2类白名单操作，默认单次最多影响100行；必须预览、确认、复验，并用事务回执判断是否已提交。

Output · SkillResult

Shared ToolW08

MySQL InnoDB事务

唯一回执→原子版本复验→业务变更→审计→完成回执→COMMIT。

duplicate → 查原回执 / out: audit_id
读写边界：受控写入Skill只调用只读接口生成变更预览，不承担用户普通查询；查询失败可重试，写入断线后必须先查回执。
范围边界：缺少必填条件或预计影响超过100行时返回WRITE_SCOPE_TOO_LARGE；不自动分页或拆批，大批量变更不进入在线Agent链路。
提交结果未知：SQLite只保存Agent状态；业务结果必须按operation_id查询MySQL主库回执。已提交则返回原结果，确认未提交才允许同ID重试，无法确认则标记UNKNOWN。该ID只防止同一次操作被重复执行。
并发边界：预览阶段不持锁；最终事务使用WHERE id/version或锁定读原子复验。业务表、回执表和审计表必须位于同一MySQL实例并使用InnoDB。

设计亮点

  • LLM只生成WritePlan，写SQL来自白名单参数化模板。
  • 操作回执、业务变更、审计记录同事务提交。

解决问题

  • 误写、越权、大范围变更和审批后数据漂移。
  • 连接中断后无法判断写入是否已生效。
MVP

项目边界

只实现能够强化可信查询和受控写入的能力。

包含

  • 单Coordinator与两个Skill
  • 指标语义层、Schema Agentic RAG与三个公共Tool
  • MetricCompiler、实时数据候选澄清、SqliteSaver状态持久化
  • 基于QueryTask与result_id的受限多轮查询
  • 有界结果落盘、TTL清理、表格分页与CSV
  • 1～2类明确目标的白名单写入、单次最多100行、HITL与同一操作防重

不包含

  • 数据计算Skill、任意Python代码和计算沙箱
  • 图表报告Skill、自动图表与报告生成
  • Multi-Agent、子Agent和复杂任务DAG
  • 预测、聚类、跨数据源分析和长期用户记忆
  • 临时结果上的任意SQL和开放式二次计算
  • 分库分表、按页回查业务库和无限明细导出
  • 通用写入、在线大批量写入和已提交操作的一键回滚
  • 多实例部署、SQLite多写节点和跨数据库事务
计算边界：GMV、同比、环比、占比、TopN和贡献度通过CTE、条件聚合或窗口函数一次完成；SQL无法表达时返回UNSUPPORTED_ANALYSIS。
风险控制：SQLGlot只负责解析，数据库最小权限和运行时限制负责兜底；HITL节点无前置副作用；Parquet通过临时文件、状态机和读删锁保证完整性。
S0

状态与通信

共享State只放协调信息；Skill内部过程隔离；大数据通过引用传递。

Runtime Context

单次请求

用户、租户、实时权限、服务端时间、业务时区和数据库连接。

SQLite

Coordinator State

SqliteSaver保存上一轮QueryTask、澄清信息、result_id和operation_id。

Skill State

调用内私有

Schema补检、查询骨架修复、写入预览和重试过程。

SQLite + Parquet

Result Store

SQLite保存所有者、parent_result_id、状态与TTL；Parquet使用临时文件、原子重命名和读删锁。

存储契约：MySQL是业务事实源，SQLite是Agent控制面，Parquet是临时结果面。SQLite状态不能作为MySQL写入已提交的证据。
